# ADR 002: 教务扫码登录 — 预热浏览器 vs 每次 Launch

**状态**: 已采纳  
**日期**: 2026-07-05  
**决策者**: 周鉦罡

## 背景

企业微信扫码登录需要 Playwright 无头浏览器代理 CAS 认证页面。
N100 只有 4 核 7.5GB 内存，`chromium.launch()` 每次约 10-15 秒，开学高峰多个学生同时扫码会让最先请求的用户等很久。

## 决策

**复用单例预热浏览器 + 每个会话创建独立 BrowserContext**：

- 进程启动时预热一个 Chromium 实例（`getWarmBrowser()`），常驻内存
- 每个扫码会话创建独立 `browser.newContext()` → 隔离 Cookie、状态
- 扫码完成后只释放 context/page，浏览器进程保持存活
- 浏览器意外断开时自动重建

## 替代方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 每次 launch（旧方案） | 隔离性强，崩溃不互相影响 | 首个用户等 15s，体验差 |
| 浏览器进程池（N 个常驻） | 并发高 | N100 内存不够，6 个并发已到 1.5GB |
| 纯 HTTP 逆向 CAS | 零浏览器开销 | CAS 带反自动化参数，维护成本高 |

## 后果

- 首次请求仍需等浏览器启动（10-15s），但后续请求毫秒级响应
- 进程重启后第一个扫码用户仍然是"倒霉用户"
- `MAX_CONCURRENT_BROWSERS = 6` + 等待队列 30s 机制缓解高峰期排队
